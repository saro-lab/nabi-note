# بنیادی استعمال

یہ npm والا راستہ ہے۔ ایک `<script>` سطر سے استعمال کا راستہ
[{{ t('menu_intro_cdn') }}](./cdn) میں ہے۔

```sh
npm i nabi-note
```

---

## ٹکڑوں کو جوڑنا

میزبان جگہ بناتا ہے اور mount ایک ایک کر کے جوڑتا ہے۔ نیچے کم از کم ترتیب ہے، اور
ہر wing کی دستاویز میں دکھائی جانے والی مثال اسی ڈھانچے میں ایک دو wing جوڑنے کی
شکل ہوتی ہے۔

```html
<div id="app" class="nabi">
  <div id="chrome" class="nabi-toolbar">
    <div id="toolbar"></div>
    <div id="context"></div>
  </div>
  <div id="editor" class="nabi-content" contenteditable="true"></div>
</div>
```

```ts
import {
  createNabiWith,
  mountSurface,
  mountToolbar,
  mountContextToolbar,
  mountHints,
  mountViewTools,
  mountSticky,
  watchSettle,
  parseNodes,
  boldWing,
  italicWing,
} from 'nabi-note'
import 'nabi-note/nabi.css'

const app = document.querySelector<HTMLElement>('#app')!
const surface = document.querySelector<HTMLElement>('#editor')!

// wing کی فہرست ایک ساتھ اصناف کی معرفت، command اور جوڑنے والا بناتی ہے — یہی `registry` ہے
const { nabi, registry } = createNabiWith([boldWing, italicWing], {
  parseHtml: parseNodes,
})

mountSurface({ nabi, registry, root: surface })

const settle = watchSettle(document, { surface })
const shared = { nabi, registry, surface, settle, locale: 'ur' }

const toolbar = mountToolbar({ ...shared, root: document.querySelector<HTMLElement>('#toolbar')! })
const context = mountContextToolbar({ ...shared, root: document.querySelector<HTMLElement>('#context')! })

mountHints({ toolbar, context, root: document.querySelector<HTMLElement>('#chrome')!, surface })
mountViewTools({ nabi, surface, root: app, container: document.querySelector<HTMLElement>('#toolbar')!, locale: 'ur' })
mountSticky({ root: app, surface })

// قدر بدلنے پر — یہاں اپنا کوڈ لگائیں
// nabi.onChange(() => user_callback(nabi.getHtml()))
```

جگہ میزبان بناتا ہے، مگر **اس جگہ کی شکل کور جانتا ہے** — mount خود اپنے ظرف پر
`.nabi-toolbar-row`·`.nabi-context`·`.nabi-editing` لگا دیتا ہے، اور آلات کا ڈبہ
بھی خود کھڑا کرتا ہے۔ مطلب یہ کہ میزبان کو خود سے ترتیب بنانے کی ضرورت نہیں، اسی
لیے اوپر کے مارک اپ میں صرف تین کلاسیں ہیں۔

- **`class="nabi"`** — رنگ کے ٹوکن اور سٹائل شیٹ صرف اسی کے اندر رہتے ہیں۔ یہ وہ
  ڈبہ بھی ہے جسے مکمل سکرین پوری طرح جما دیتی ہے، اس لیے ٹول بار اور ترمیمی حصہ
  **دونوں** اس کے اندر ہونا ضروری ہیں۔
- **`class="nabi-toolbar"`** — ٹول بار سطر اور سیاق سطر کو ایک ٹکڑا بنا کر **اوپر
  چپکاتا (sticky) ہے۔** دونوں الگ چپکیں تو سیاق سطر ابھرنے پر متن دھکیلا جاتا ہے
  اور سکرین ہلتی ہے۔
- **`class="nabi-content" contenteditable`** — ترمیمی حصہ خود۔

اگر سائٹ پر کوئی مقررہ ہیڈر ہے تو `--nabi-sticky-top` سے اتنا نیچے کر دیں، اور
`mountSticky()` لگا لیں تو موبائل کی بورڈ نے سکرین کو جتنا دھکیلا اسے کور خود
ناپ کر واپس کر دیتا ہے۔

**سٹائل شیٹ میزبان لگاتا ہے۔** bundler استعمال کریں تو `import 'nabi-note/nabi.css'`
ایک سطر کافی ہے، اور صرف رجسٹر شدہ wing کا CSS چاہیے تو
`injectSheets(document, collectSheets(registry))` بلائیں۔ **جو صفحہ دستاویز کو سرور پر
پہلے سے کھینچ کر بھیجتا ہے وہاں فائل والا راستہ اپنائیں** — انجیکشن ایڈیٹر کا
JavaScript پہنچنے کے بعد ہی لگتا ہے، اس دوران دستاویز ایک بار ننگی نظر آ جاتی ہے۔

**یہی بات لکھائی کی سمت بھی طے کرتی ہے۔** عربی (`ar`) یا اردو (`ur`) دیں تو اُس mount
کی جڑ پر `dir="rtl"` لگ جاتا ہے اور دائیں سے بائیں کھڑا ہوتا ہے — صفحہ `<html dir>` سے
کچھ نہ بھی کہے تب بھی۔ `locale` **نہ دیں تو کور اسے چھوتا نہیں** — سمت کو خود سنبھالنے
والے میزبان کی مرضی پر دخل نہیں دیتا۔ کون سی زبان کس سمت میں ہے، یہ `localeDirection(code)`
بتاتا ہے۔

```ts
mountSurface({ nabi, registry, root: surface, locale: 'ur' })   // ترمیمی حصہ RTL میں
mountToolbar({ nabi, registry, surface, root: toolbar, locale: 'ur' })   // ٹول بار بھی آئینے کی طرح
```

دکھانے کی زبان ہر mount میں `locale` سے طے ہوتی ہے — دستاویز کا متن ویسا ہی رہتا
ہے، صرف ٹول بار اور سیاق سطر کے نام بدلتے ہیں۔ **میزبان کو locale صرف ایک بار اعلان
کرنا ہوتا ہے** — اوپر کی مثال کی طرح ایک ہی گٹھڑی (`shared`) میں رکھ کر تمام mount کو
دیں تو ٹول بار کھڑے ہوتے ہی اپنا `locale` کور پر بھی لگا دیتا ہے (`nabi.$bindLocale`)،
اس لیے کور کی اپنی باتیں (toast وغیرہ) بھی اسی زبان میں نکلتی ہیں۔ جہاں ٹول بار نہیں
لگایا وہاں `createNabiWith` کے آپشن میں `locale` دیں۔ منتخب کرنے والا (picker) بنانا ہو
تو پیکج کی نکالی ہوئی `LOCALES` (کوڈ کی فہرست) استعمال کریں۔

| تعمیر | لازمی | کام |
|---|---|---|
| `createNabiWith(wings, options?)` | ہاں | `{ nabi, registry }` واپس دیتا ہے۔ DOM کی ضرورت نہیں۔ wing کی صف بھی، چننے والا builder (`wings()`، دیکھیں [{{ t('menu_intro_cdn') }}](./cdn#wing-چننا)) بھی، جوں کا توں قبول کرتا ہے |
| `mountSurface({ nabi, registry, root })` | ہاں | کیریٹ، IME اور ان پٹ کو nabi-tree سے دوبارہ ملاتا ہے۔ رجسٹر شدہ wing کا `attach` بھی ساتھ لگاتا ہے |
| `mountToolbar({ nabi, registry, root, surface?, locale?, file? })` | نہیں | مین ٹول بار۔ اس کے بغیر بھی `applyCommand()` سے براہِ راست ترمیم ممکن ہے۔ `mountFile()` کا جواب `file` میں دیں تو **محفوظ کرنے کا panel بغیر جوڑے کھڑا ہو جاتا ہے** — محفوظ کرنے کا بٹن اور <kbd>⌘</kbd><kbd>S</kbd> اسے کھولتے ہیں۔ نہ دیں تو پہلے کی طرح دبانا `onHost('save')` سے میزبان کو آتا ہے۔ `surface` وہ **زمین بھی ہے جس پر accelerator زندہ ہیں** (نیچے [جہاں accelerator سنے جاتے ہیں](#جہاں-accelerator-سنے-جاتے-ہیں) دیکھیں) |
| `mountContextToolbar({ nabi, registry, root, surface? })` | نہیں | کیریٹ کی جگہ کے مطابق سیاق سطر (جدول کی قطار و کالم، کوڈ کی زبان، لنک کا پتہ و نام وغیرہ) |
| `mountHints({ toolbar, context?, root, surface? })` | نہیں | Shift دو بار دبانے پر نکلنے والا شارٹ کٹ بیج |
| `mountViewTools({ nabi, surface, root, container, onBody? })` | نہیں | پیش نظارہ اور مکمل سکرین کے دو بٹن۔ `root` وہ `.nabi` ڈبہ ہے جسے مکمل سکرین جمائے گی، `onBody` پیش نظارے کے متن پر پڑھنے والی طرف کا runtime جوڑنے کا hook ہے (نیچے) |
| `mountSticky({ root, surface, chrome?, nabi? })` | نہیں | موبائل کی بورڈ نے سکرین کو جتنا دھکیلا اس کے مطابق چپکا ہوا ٹول بار واپس کرتا ہے۔ `nabi` دیں تو **ترمیم کے بعد کیریٹ ٹول بار میں جتنا دبا ہو اتنا خود دھکیلتا ہے** — نہ دیں تو پہلے کی طرح صرف میزبان کے `aim()` بلانے پر چلتا ہے (نیچے [موبائل کی بورڈ](#موبائل-کی-بورڈ-اور-چپکنے-والا-ٹول-بار) دیکھیں) |
| `mountPickedMark({ nabi, surface })` | نہیں | تصویر یا ویڈیو چننے کا نشان (براؤزر خود نہیں دکھاتا) |
| `mountFile({ nabi, store, registry, parse?, name? })` | save·open استعمال کریں تو | `.nabi`·`.nhtml`·`.md` **تین** فارمیٹ میں محفوظ کرتا ہے، اور ان تینوں کے ساتھ باہر سے آئے سادہ `.html` کو ملا کر **چار** کھولتا ہے۔ **`registry` لازمی ہے** — فارمیٹ کی فہرست اور md·HTML کی تعمیر دونوں وہیں سے آتی ہیں۔ `parse` HTML پڑھنے کا دروازہ ہے؛ براؤزر میں نہ دیں تو `parseNodes` خود کھڑا ہو جاتا ہے، مگر سر کے بغیر جگہ (سرور، ٹیسٹ) میں `.nhtml`·`.html` کھولنے کے لیے خود دینا لازم ہے۔ جواب میں ملنے والا `FileMount` ہی **wing کے بغیر محفوظ کرنے اور کھولنے کا اصل دروازہ ہے** (`file.save()` · `file.saveAs(id, name)` · `file.formats()` · `await file.open()`) |
| `mountLocalHistory({ nabi, storage })` | localHistory استعمال کریں تو | مقررہ وقفے پر براؤزر میں ریکارڈ کرنا۔ `storage` کے `null` ہونے پر بھی (جیسے بند `file://` جگہ) کھڑا ہوتا ہے — تاکہ بٹن کیوں نہیں چلتا یہ toast سے بتا سکے |
| `mountUpload({ … })` + `mountUploadView({ … })` | upload استعمال کریں تو | ڈراپ، پیسٹ یا فائل چننے کی اپ لوڈ پیش رفت اور اس کا اظہار |

**تصویر، چیک، جدول کے خانے کو گھسیٹنا اور کوڈ کی رنگ کاری کے لیے الگ سے کوئی mount
نہیں چاہیے** — یہ سب wing خود `attach` سے اٹھائے ہوتی ہے، اور `mountSurface` انہیں
خود ساتھ لگا دیتا ہے۔ کوڈ کی رنگ کاری کے لیے صرف رنگ کرنے والا جوڑ دیں
(`makeCodeAttach`، دیکھیں [{{ t('menu_block_code') }}](../wing/block/code))۔

### خالی ایڈیٹر کی رہنما تحریر

خالی ایڈیٹر پہلی سطر پر ایک ہلکی رہنما تحریر دکھاتا ہے۔ ایک بھی حرف لکھنے پر یہ فوراً
غائب ہو جاتی ہے، اور مٹا کر دوبارہ خالی کریں تو دوبارہ لوٹ آتی ہے۔ **کچھ کیے بغیر بھی نظر
آتی ہے** — یہ متن کور کی اپنی لغت سے آتا ہے، اس لیے اُس mount کی زبان کی پیروی کرتا ہے۔
جگہ کا تعین **لکھائی کی سمت** کرتا ہے (LTR میں بائیں، RTL میں دائیں) — سطر خود درمیان یا
دائیں سیدھ میں ہو تب بھی رہنما تحریر اس کی پیروی نہیں کرتی۔

```ts
mountSurface({ nabi, registry, root: surface, placeholder: 'یہاں نوٹ لکھیں' })
mountSurface({ nabi, registry, root: surface, placeholder: 'پہلی سطر\nدوسری سطر' })   // کئی سطریں
mountSurface({ nabi, registry, root: surface, placeholder: '' })   // بغیر رہنما تحریر
```

لائن بریک (`\n`) جوں کا توں سطر بن جاتا ہے۔ مگر رہنما تحریر **بہاؤ سے باہر** کھڑی ہوتی ہے
(کیریٹ کو دھکیلنے سے بچنے کے لیے)، اس لیے ترمیمی حصہ اس سے چھوٹا ہو تو کئی سطروں والی رہنما
تحریر نیچے سے باہر بہہ جاتی ہے۔ خالی ترمیمی حصہ default طور پر پہلے سے `12.5rem` اونچا کھڑا
ہوتا ہے، اس لیے اکثر اسے چھیڑنے کی ضرورت نہیں پڑتی؛ اور اونچائی چاہیے ہو تو
`--nabi-content-min-height` سے بڑھائیں۔ یہ قدر **صرف ترمیمی سطح پر** لگتی ہے — شائع شدہ یا
پیش نظارے والی دستاویز پر متن خود ہی اونچائی طے کرتا ہے۔

**رہنما تحریر ایک الگ تہہ ہے۔** یہ ترمیمی جڑ کے `::before` پر جا کھڑی ہوئی ہے، اس لیے
**دستاویز کی ساخت سے بے اثر رہتی ہے** — پہلی سطر سرخی ہو، درمیان میں ہو یا ڈراپ کیپ پہنے
ہو۔ صرف لکھائی کی سمت اس کی جگہ طے کرتی ہے۔

یہ متن ترمیمی حصے کی جڑ پر `--nabi-placeholder` میں جاتا ہے، اور کھینچنے کا کام سٹائل شیٹ
کرتی ہے۔ رنگ یا وزن بدلنا ہو تو یہ قاعدہ دوبارہ لکھیں۔

```css
.nabi-content.nabi-editing:has(> :is(p, h1, h2, h3, h4, h5, h6):only-child > br:only-child)::before {
  color: #999;
}
```

صرف رنگ بدلنا ہو تو پورا قاعدہ دوبارہ لکھنے کی ضرورت نہیں — `--nabi-placeholder-color` ایک
سطر ہی کافی ہے۔

### جہاں accelerator سنے جاتے ہیں

<kbd>⌘</kbd><kbd>S</kbd> جیسے accelerator سننے کی جگہ ایک ہی ہے، اور وہ ٹول بار ہے۔ اس کا
کان کہاں تک پہنچتا ہے یہ `mountToolbar({ surface })` طے کرتا ہے — **صرف اسی surface یا ٹول
بار کی سطروں میں اٹھی کلید** اس ایڈیٹر کی مانی جاتی ہے۔

- **ایک صفحے پر دو ایڈیٹر ہوں تو `surface` ضرور دیں۔** نہ دیں تو ٹول بار پورے دستاویز کو
  سننے پر واپس چلا جاتا ہے، اور تب نیچے والے ایڈیٹر میں دبائی گئی <kbd>⌘</kbd><kbd>S</kbd>
  اوپر والے ایڈیٹر کا متن محفوظ کر دیتی ہے۔ میزبان کے اپنے سادہ ان پٹ خانے میں دبائی گئی
  کلید تک لے لی جاتی ہے۔
- **کوئی wing رجسٹر نہ کریں تو وہ کلید سرے سے موجود ہی نہیں۔** محفوظ کرنا اور کھولنا کور
  (`mountFile`) میں رہتے ہیں، مگر بٹن اور accelerator wing کے ہیں — اس لیے صرف
  `wings().allBasic()` سے کھڑے ایڈیٹر میں <kbd>⌘</kbd><kbd>S</kbd> اور
  <kbd>⌘</kbd><kbd>O</kbd> نہیں ہوتیں۔ واپس لانے کا ایک ہی راستہ ہے —
  `.use('save').use('open')`۔
- **کہیں نہ پہنچے تو کلید نگلی نہیں جاتی۔** جس ترتیب میں محفوظ کرنے کا بٹن کہیں نہیں پہنچتا
  (نہ `file` نہ `onHost` ٹول بار میں جوڑا) وہاں کلید براؤزر کی اپنی سمجھ کر آگے بہہ جاتی ہے۔
  جو کام ہم نہیں کرتے اس کا شارٹ کٹ چھیننا نہیں — خاموشی سے نگل لیں تو پڑھنے والا سمجھتا ہے
  اس کا براؤزر خراب ہے۔

wing کے بغیر محفوظ کرنا اور کھولنا ہو تو `mountFile` کا دیا ہوا ہینڈل استعمال کریں — بغیر
بٹن اور بغیر accelerator والے ایڈیٹر میں میزبان خود `file.save()` اور `file.open()` بلائے۔

### موبائل کی بورڈ اور چپکنے والا ٹول بار

`mountSticky` اب موبائل پر مزید کام کرتا ہے — کی بورڈ کھڑا اور لیٹا ہونا دیکھ کر کیریٹ کو
**ٹول بار کے نیچے اور کی بورڈ کے اوپر** لے آتا ہے۔ میزبان کو تین چیزیں معلوم ہونی چاہئیں۔

- **صرف ایڈیٹر پر focus ہونے کے دوران ہی حرکت کرتا ہے۔** focus کہیں اور ہو تو ایک قدم بھی
  نہیں چلتا — میزبان `setHtml()` سے قدر ڈال رہا ہو تب صفحہ اچھلنا نہیں چاہیے۔
- **ہاتھ سکرول کر رہا ہو تو ایک پکسل بھی نہیں ہلتا۔** سکرول کے بعد 250ms تک لاک رہتا ہے —
  چلتی سکرین کو ہاتھ سے چھیننا ہی لرزش کی اصل شکل ہے۔
- **صرف کی بورڈ جتنی بڑی تبدیلی پر دروازہ کھلتا ہے۔** ایڈریس بار کا سمٹنا (چند دس پکسل) کچھ
  نہیں ہلاتا؛ دروازہ صرف `max(120px, ونڈو کی اونچائی کا 15%)` سے بڑی تبدیلی پر کھلتا ہے۔

ٹائپ کرنا سکرین کو **جتنا ضروری ہو اتنا ہی** دھکیلتا ہے — ہر حرف پر سکرین کو ٹول بار تک
کھینچنا ناقابلِ استعمال ہو جاتا۔ البتہ کی بورڈ کھڑے ہونے کے لمحے، جگہ کو یوں ملایا جاتا ہے کہ
**ٹول بار ونڈو کے بالکل اوپر بیٹھے**، اور viewport ٹھہرنے کے بعد ایک بار پھر ملایا جاتا ہے۔

`--nabi-bar-height` وہی قدر ہے جو یہ قدم استعمال کرتا ہے — `mountSticky` جس chrome سے جڑا
ہے اس کی **حقیقی ناپی گئی اونچائی** `.nabi` جڑ پر لکھ دیتا ہے، اور سٹائل شیٹ کا
`.nabi-content > *` وہ قدر `scroll-margin-block-start` میں جوڑ لیتا ہے۔ **یہ میزبان کے ہاتھ
سے لکھنے کی قدر نہیں بلکہ اس بات کی وضاحت ہے کہ کیریٹ ٹول بار کے نیچے کبھی کیوں نہیں چھپتا**
— mount نہ ہو تو بجائے اس کے اندازاً `3.5rem` کھڑا ہوتا ہے، جو ٹول بار دو سطروں میں لپٹے یا
سیاق سطر اوپر ہو تو کافی نہیں پڑتا۔

::: warning viewport میٹا سے زوم مت روکیں
iOS سفاری فوکس 16px سے چھوٹے فارم خانے پر جائے تو پورا صفحہ زوم کر دیتا ہے۔ کور اسے
**متن بڑا کر کے** روکتا ہے — `--nabi-touch-font-size` (default `16px`)۔ زوم کو ہی
`user-scalable=no` یا `maximum-scale=1` سے روکنے کا دوسرا راستہ ہم نے **نہیں چنا** — وہ
پڑھنے والے سے زوم کرنے کا حق چھین لیتا ہے۔ میزبان اپنے صفحے پر وہ میٹا لکھے تو کور کی رکھی
بنیادی قدر بے معنی ہو جاتی ہے — اس لیے وہ میٹا نہ لکھیں۔
:::

### پیش نظارے پر پڑھنے والی طرف کا runtime جوڑنا

پیش نظارہ `getHtml()` کو جوں کا توں لگایا گیا جامد HTML ہے، اس لیے جدول کی ترتیب اور
کوڈ کی رنگ کاری جیسا **پڑھنے والی طرف کا JavaScript کام** خود بخود نہیں جڑتا۔
`nabi-note/viewer` کا `attachViewer` وہ سب ایک دروازے سے جوڑ دیتا ہے، اور پیش نظارے میں
جوڑنے کی جگہ `onBody` ہک ہے — اوپر کی کم از کم ترتیب کی `mountViewTools` سطر کو اس طرح
بدل دیں۔

```ts
import { attachViewer } from 'nabi-note/viewer'

mountViewTools({
  nabi,
  surface,
  root: app,
  container: document.querySelector<HTMLElement>('#toolbar')!,
  locale: 'ur',
  onBody: (body) => attachViewer(body, { locale: 'ur' }),
})
```

`onBody` پیش نظارے کا متن کھڑا ہوتے وقت بلایا جاتا ہے، اور جواب میں دی گئی ہٹانے والی
فنکشن ڈھکن بند ہونے پر بلائی جاتی ہے۔ شائع شدہ صفحے پر بھی **وہی ایک سطر**
(`attachViewer`) جوڑیں — پیش نظارہ شائع شدہ صفحے جیسا ہی ہونا چاہیے، اس لیے دونوں پر
ایک ہی دروازہ جوڑنا اسی hook کا مقصد ہے۔ تفصیل
[{{ t('menu_intro_cdn') }} ▸ پڑھنے والی سکرین](./cdn#پڑھنے-والی-سکرین) میں ہے۔

کوڈ کی رنگ کاری built-in tokenizer بنیادی طور پر دیتا ہے (dependency صفر)۔ Shiki جیسا
ہائی لائٹر استعمال کرنے والا میزبان `attachViewer(body, { locale, highlight })` سے وہی
hook دیتا ہے — `makeCodeAttach({ highlight })` کو دیے گئے کے ساتھ ایک جیسا رکھیں تو
ترمیمی سکرین اور پڑھنے والی سکرین کا رنگ الگ نہیں ہوتا۔

wing بدلنی ہو تو یہ سارا ٹکڑا اکٹھا کریں (`unmount()`) اور نئے سرے سے بنائیں —
ہٹائی گئی wing جو مارک اپ رکھتی تھی وہ اسی جگہ سادہ متن بن کر گر جاتا ہے۔ اس سائٹ
کا ڈیمو دراصل اسی طرح چلتا ہے — wing کا چپ بند کر کے دوبارہ کھولیں تو تعمیر پوری
دوبارہ بنتی ہے۔

رنگ اور شکل کے CSS متغیرات [{{ t('menu_style_custom') }}](../style/custom) میں
ہیں۔

## دستاویز نکالنے کے تین طریقے

```ts
nabi.getHtml()        // محفوظ کرنے اور شائع کرنے کے لیے HTML
nabi.getJson()        // nabi-tree (JSON)
nabi.getEditorHtml()  // ابھی ایڈیٹر سکرین کا HTML (اس پر data-key لگا ہے)
```

**محفوظ کرنے کی قدر پہلے دو میں سے ایک ہے۔** `getEditorHtml()` پر سکرین کا خاص
نشان (`data-key`) لگا ہے، یہ باہر بھیجنے والی قدر نہیں — یہ جگہ سرور سے ایڈیٹر
پہلے سے کھینچ کر بھیجنے (SSR) کے لیے ہے۔

باہر جانے والا JSON اس طرح دکھتا ہے۔ **دستاویز بلاکس کی ایک صف ہے،** اسے لپیٹنے
والی کوئی جڑ node نہیں ہے۔

```json
[
  {"w":"p","a":{"h":2},"ch":["عنوان"]},
  {"w":"p","ch":["متن ",{"w":"b","ch":["جلی"]}," اور ",
    {"w":"a","a":{"href":"https://nabi.saro.me/"},"ch":["لنک"]}]},
  {"w":"p","a":{"a":"c"},"ch":["درمیان"]},
  {"w":"p","ch":[{"w":"ul","ch":[
    {"w":"li","ch":[{"w":"p","ch":["ایک"]}]},
    {"w":"li","ch":[{"w":"p","ch":["دو"]}]}]}]}
]
```

پڑھنے کے قواعد صرف چار ہیں۔

- **`w` وہ wing کا id ہے جو اُس node کو کھینچتا ہے۔** محفوظ الفاظ صرف دو ہیں —
  `p` (پیراگراف) اور `br` (سطر) — باقی سب رجسٹر کی گئی wing کے id ہیں، جیسے `b`،
  `ul`، `li`۔ سرخی الگ wing نہیں بلکہ **پیراگراف کی خاصیت** ہے
  (`{"w":"p","a":{"h":2}}`)۔
- **سٹرنگ ہو تو حرف، آبجیکٹ ہو تو wing۔** صنف بتانے کے لیے کوئی الگ خانہ نہیں۔
- **`a` وہ قدر ہے جو اُس wing نے تھامی ہے** — لنک کا پتہ، ہائی لائٹ کا رنگ، سرخی
  کا درجہ وغیرہ۔ قدر نہ ہو تو خانہ بھی نہیں ہوتا۔ سیدھ کی قدر بھی `a` ہی ہے مگر
  یہ اسی خانے کے **اندر** بیٹھی ہے، اس لیے الجھن نہیں ہوتی
  (`{"w":"p","a":{"a":"c"}}` — درمیان میں سیدھا کیا گیا پیراگراف)۔
- **جدول، فہرست، تصویر جیسی چیز جو پیراگراف کی جگہ لیتی ہے اسے ایک پیراگراف ایک
  تہہ میں لپیٹتا ہے** (اوپر `ul` دیکھیں)۔ وہی پیراگراف سیدھ اٹھاتا ہے، اور کیریٹ
  کو اُس چیز کے آگے پیچھے کھڑا ہونے کی جگہ یہی دیتا ہے۔ HTML میں یہ
  `<div data-nabi-p>` بن کر نکلتا ہے — کیونکہ `<p>` قواعد کے لحاظ سے جدول یا
  فہرست کو نہیں سما سکتا۔

اندر گھومنے والی ٹری میں ہر node پر ایک اضافی کلید `_id` بھی ہوتی ہے — یہ **وہ
اندرونی پتہ ہے جس سے کیریٹ node کو پکڑتا ہے،** زیادہ تر ترمیم میں نئے سرے سے دیا
جاتا ہے، اور باہر جاتے وقت اتار دیا جاتا ہے (اوپر کی مثال میں 470 سے 323 بائٹ)۔
باہر نکلی ہوئی قدر کو سیدھا `setJson()` میں دوبارہ ڈال دیا جا سکتا ہے۔

## دستاویز اندر ڈالنے کے چار طریقے

```ts
createNabiWith(wings, { doc })   // پہلے سے بنے ہوئے nabi-tree سے شروع
nabi.setJson(json)               // nabi-tree سے پورا بدل دینا
nabi.setHtml(html)               // HTML سٹرنگ سے پورا بدل دینا
nabi.applyCommand('setHeading', { value: 2 })  // ترمیمی command (وہی دروازہ جو wing استعمال کرتی ہے)
```

چاروں **کامیابی یا ناکامی کا جواب `boolean` سے دیتے ہیں۔** exception نہیں پھینکتے،
اور ناکام ہوں تو دستاویز کو ہاتھ نہیں لگاتے۔

| جہاں جواب `false` ہو | |
|---|---|
| `setJson` | nabi-tree کی شکل نہیں ہے (خالی قدر الگ ہے — نیچے دیکھیں) |
| `setHtml` | `parseHtml` اڈاپٹر نہیں جوڑا گیا (نیچے دیکھیں) یا ترمیم لاک ہے (خالی قدر الگ ہے) |
| `applyCommand` | ایسا کوئی command نہیں، یا **کچھ بدلا ہی نہیں** |

**خالی دستاویز کی شکل ایک ہی ہے — `[{"w":"p","ch":[]}]`۔** پوری تحریر منتخب کر کے
مٹانے جیسے کسی عمل سے سب کچھ صاف ہو تو پہلے بلاک کی سرخی یا سیدھ باقی نہیں رہتی۔ کئی
سطروں میں سے صرف ایک سطر خالی کرنا الگ بات ہے — وہاں دوبارہ لکھنے کا ارادہ ہوتا ہے، اس
لیے اُس پیراگراف کی خاصیت ویسی ہی رہتی ہے۔

**خالی قدر شکل کی غلطی نہیں، خالی دستاویز ہے۔** `null`، `undefined`، خالی سٹرنگ (صرف
خالی جگہ والی بھی) یا خالی صف دیں تو رد نہیں ہوتا — **خالی سکرین بیٹھتی ہے اور `true`**
جواب آتا ہے، یہ `setJson` اور `setHtml` دونوں پر یکساں ہے، اسی لیے "خالی کرنا" ہمیشہ
کامیاب رہتا ہے۔ خالی قدر میں پڑھنے کو کچھ نہیں ہوتا، اس لیے اُس وقت `setHtml` کو
اڈاپٹر (نیچے) کی بھی ضرورت نہیں۔ غلط شکل والی قدر اب بھی رد ہوتی ہے — خالی اور غلط دو
مختلف باتیں ہیں۔

آخری سطر ایک قاعدہ ہے — **کچھ نہ بدلے تو خاموشی ہے۔** پہلے سے سطح 2 کی سرخی والے
پیراگراف پر دوبارہ `setHeading` لگائیں تو جواب `false` آتا ہے، نہ undo کا نکتہ
بنتا ہے نہ کوئی سگنل نکلتا ہے۔

`applyCommand` کا تیسرا argument **بلانے والا ہاتھ** ہے — `applyCommand(name, args?, by?)`
کا `by` قسم `CommandHand` (`'keyboard' | 'pointer'`) رکھتا ہے اور نہ بتائیں تو
`'keyboard'` مانا جاتا ہے۔ فرق ایک ہی جگہ پڑتا ہے: کیریٹ بند ہونے کی حالت میں mark
command کیبورڈ سے آئے تو محفوظ ہو جاتا ہے (اگلے حرف سے لاگو)، پوائنٹر سے آئے تو محفوظ
ہوئے بغیر `false` جواب دیتا ہے اور "لگانے کے لیے کچھ منتخب نہیں" کہہ کر toast دکھاتا
ہے۔ اپنا UI بنا کر command بلانے والے، کلک کے ہینڈلر میں `'pointer'` ضرور بتائیں۔

### `setHtml` کو اڈاپٹر کی ضرورت ہے

HTML پڑھنے کا کام براؤزر کا `DOMParser` کرتا ہے۔ کور DOM کو نہیں جانتا، اس لیے
اعلان کے وقت وہ اڈاپٹر جوڑ دیں۔

```ts
import { createNabiWith, parseNodes } from 'nabi-note'

const { nabi } = createNabiWith(wings, { parseHtml: parseNodes })
```

`setJson` کو اڈاپٹر کی ضرورت نہیں — محفوظ کیا گیا JSON **سرور (Node.js) پر بھی
جوں کا توں** ڈالا جا سکتا ہے۔ جوڑنا (`getHtml`) بھی DOM استعمال نہیں کرتا، اس لیے
سرور پر JSON پڑھ کر HTML بنا کر بھیجنے کا راستہ کھلا رہتا ہے۔

## پیسٹ، محفوظ کرنا اور کھولنا

**پیسٹ ایک ہی کلپ بورڈ کو کئی نظروں سے پڑھتا ہے** — `HTML`·`MARKDOWN`·`TEXT`، اور نابی کا
اپنا فارمیٹ (`NABI`)۔ پڑھنے کے دو یا زیادہ راستے کھڑے ہوں تو ایک چھوٹا panel پوچھتا ہے کس سے
پیسٹ کرنا ہے، صرف ایک ہو تو بغیر پوچھے پیسٹ ہو جاتا ہے۔ جس پیسٹ میں کوئی حرف ہی نہ ہو (صرف
فائل) وہ panel کو چھوڑ کر [{{ t('menu_etc_upload') }}](../wing/etc/upload) کو جاتا ہے۔

**محفوظ کرنے کے فارمیٹ تین ہیں** — `.nabi` (اصل) · `.nhtml` (اکیلا کھلنے والا HTML کا ایک
صفحہ) · `.md` (مارک ڈاؤن؛ جس کی جگہ وہاں نہیں وہ HTML بن کر مل جاتا ہے، اس لیے وہ واپس نہ آ
سکے)۔ **کھلتے چار ہیں** — یہی تین اور باہر سے آیا سادہ `.html`۔ یہ دروازہ کھڑا ہونے کے لیے
اوپر کے جدول کا `mountFile()` جڑا ہونا لازم ہے، اور ایک اور فارمیٹ جوڑنے کا راستہ
[{{ t('menu_wing_custom') }}](../wing/custom#io-فلٹر-جوڑنا) میں ہے۔

## اطلاعات toast سے نکلتی ہیں

اپ لوڈ کی خرابی، مقامی ریکارڈ کی اطلاع، "لگانے کے لیے کچھ منتخب نہیں" جیسی ایک سطر —
یہ سب **ایک ہی toast راستے** سے نکلتی ہیں۔ بنیادی ڈبہ کور خود رکھتا ہے، اس لیے کچھ نہ
جوڑیں تو بھی چلتا ہے — ٹول بار کھڑا ہو تو اس کے نیچے ایک مقررہ جگہ پر ظاہر ہوتی ہے
(سیاق سطر کے آنے جانے سے وہ جگہ نہیں ہلتی)۔

- درجے تین ہیں — `'info' | 'warn' | 'error'`۔ یہ کامیابی یا ناکامی کا نتیجہ نہیں،
  بلکہ **پڑھنے والے کو کتنا چوکنا ہونا چاہیے** اس کا درجہ ہے۔
- بنیادی طور پر ایک سیکنڈ بعد ہٹتی ہے (باقی 0.5 سیکنڈ سے دھندلانا شروع ہوتی ہے)، اور
  کلک کرنے سے بھی بند ہو جاتی ہے۔ ایک وقت میں زیادہ سے زیادہ 3 کھڑی ہو سکتی ہیں — اس
  سے زیادہ ہوں تو جس کا وقت سب سے کم رہ گیا ہو وہ پہلے ہٹتی ہے۔
- پیغام میں `\n` آ سکتا ہے، اور لائٹ و ڈارک دونوں میں ٹھیک نظر آتا ہے۔

انداز بدلنے کے دو آپشن اور دکھانے کا طریقہ پوری طرح بدلنے کا ایک آپشن `createNabiWith`
میں موجود ہیں۔

```ts
const { nabi } = createNabiWith(wings, {
  toastMs: 2000,   // زندہ رہنے کا وقت — بنیادی طور پر 1000ms۔ بلانے والا ہر بار الگ بھی دے سکتا ہے
  toastMax: 5,     // ایک وقت میں کھڑی ہونے کی حد — بنیادی طور پر 3
  // جس صفحے کا اپنا اطلاعی نظام ہو وہ صرف دکھانے کا طریقہ بدلتا ہے — کور کا بنیادی ڈبہ کبھی نہیں کھینچا جاتا
  // toast: (level, message, ms) => user_callback(level, message),
})
```

wing کے بولنے کا دروازہ بھی یہی ایک ہے — `nabi.$toast(level, message, ms?)`۔ وقت
پیغام کے ساتھ ہی جاتا ہے، اس لیے ایک لمبی اطلاع کے لیے پوری بنیادی قدر بدلنے کی ضرورت
نہیں۔

## ایڈیٹر کے صارف سے سوال پوچھنے کا راستہ

فائل کھولتے وقت "غیر محفوظ لکھائی موجود ہے، پھر بھی کھولیں؟" جیسا سوال چاہیے ہو
سکتا ہے۔ وہ ڈبہ **اعلان کے وقت ایک بار** جوڑا جاتا ہے۔

```ts
const { nabi } = createNabiWith(wings, {
  ask: {
    message: (text) => window.alert(text),
    confirm: (text) => window.confirm(text),
  },
})
```

| | شکل |
|---|---|
| `message` | `(text: string) => void` — ایک پیغام، کوئی جواب نہیں لیتا |
| `confirm` | `(text: string) => boolean \| Promise<boolean>` — sync یا async دونوں قبول کرتا ہے |
| `choose` | `(question: string, options: ChooseOption[]) => number \| Promise<number>` — کئی میں سے ایک۔ جواب **ایک index** ہے، اور `-1` (یا حد سے باہر کچھ بھی) منسوخی ہے۔ `ChooseOption` یعنی `{ label, icon? }`، جہاں `icon` 16×16 svg کا **اندر کا حصہ** ہے — نہ ہو تو صرف نام کھڑا ہوتا ہے |

**کور خود بخود براؤزر کے ڈائیلاگ استعمال نہیں کرتا۔** جس صفحے کا اپنا ڈائیلاگ ہو
اس میں سرمئی ڈبہ دخل نہیں دینا چاہیے، اور پلگ اِن (IntelliJ، VS Code) میں
`window.confirm` بالکل موجود ہی نہیں ہوتا۔ اوپر کی تین سطریں میزبان بناتا ہے۔

**صرف جوڑا گیا خانہ جیتتا ہے** — صرف `message` جوڑنا، یا صرف `confirm` جوڑنا، دونوں ٹھیک ہیں۔
نہ جوڑا گیا `message` کور کے toast (info) کے طور پر نکلتا ہے، اور نہ جوڑا گیا `confirm` کا
جواب "نہیں" ہے۔

**`choose` عام طور پر نہیں جوڑا جاتا۔** پیسٹ کا panel ٹول بار کھڑا ہوتے ہی خود کور پر لگ جاتا
ہے (toast والے ڈبے جیسا ہی قاعدہ)، اس لیے ٹول بار کھڑا کرنے والے صفحے کو بغیر کچھ کیے panel
مل جاتا ہے۔ یہ خانہ تبھی جوڑیں جب اپنا بنایا panel لگانا ہو۔ نہ کوئی panel لگا ہو نہ خانہ
جوڑا گیا ہو تو **جواب 0 (سب سے اوپر والا) ہے** — `confirm` کے "نہیں" سے مختلف سمت۔ یہاں
منسوخی جواب دینے سے پیسٹ سرے سے غائب ہو جائے گا، اور فہرست کا پہلا candidate ہمیشہ "سب سے
زیادہ ممکنہ پڑھت" ہوتا ہے، اس لیے پوچھنے والا نہ ہو تو یہی صحیح جواب ہے۔

::: warning نہ دیں تو `confirm` کا جواب "نہیں" ہے
جس سوال کا کوئی جواب نہ دے وہ "ہاں" نہیں ہے — یہ منسوخی، Escape یا ونڈو بند کرنے
جیسا ہی معنی رکھتا ہے۔ یہ جواب "غیر محفوظ لکھائی چھوڑ کر کھولوں؟" جیسی جگہ پر
لگتا ہے، اس لیے سوال پوچھنے والا نہ ہونے کی صورت میں چیز کو ضائع کرنے کی طرف نہیں
جانا چاہیے۔ سرور (Node) پر بھی یہی قدر خاموشی سے گزر جاتی ہے۔
:::

**یہ ایک ہی ایڈیٹر کی چیز ہے** — عالمی (global) نہیں، اس لیے ایک صفحے کے دو
ایڈیٹر مختلف انداز سے سوال پوچھ سکتے ہیں۔ wing کو بھی وہی ملتا ہے (`nabi.$ask`) —
اس کی تفصیل [{{ t('menu_wing_custom') }} ▸ UI اور برتاؤ](../wing/custom/ui) میں
ہے۔

## اس ایڈیٹر کا نام اور "کیا بدلا ہے"

```ts
nabi.sessionId   // '1755245678901-1x9k3af' — <یونکس وقت>-<nonce>، ہر انسٹینس کے لیے ایک
nabi.isChanged() // آخری بنیادی خط کے بعد دستاویز میں کچھ حرکت ہوئی یا نہیں
```

`sessionId` ایک بار بنتا ہے اور بدلتا نہیں۔ وقت بتاتا ہے کہ یہ ایڈیٹر کب کھڑا ہوا،
اسی سے ترتیب خود بخود بن جاتی ہے، اور nonce وہی ملی سیکنڈ میں کھڑے ہوئے دو
ایڈیٹروں کو الگ کرتا ہے۔ یہ خاکہ، لاگ اور خودکار محفوظ کاری کی کلید پر لگایا جانے
والا نام ہے۔

`isChanged()` کا **بنیادی خط نیا صرف تین چیزیں کھینچتی ہیں** — دستاویز کو پورا
اندر ڈالنا (`createNabiWith({ doc })`، `setJson()`، `setHtml()`) اور محفوظ ہونے
کی اطلاع۔

```ts
nabi.$markSaved(savedDoc)   // محفوظ ہو جانے کے بعد — وہی ٹری دیں جو اُس وقت محفوظ ہوئی
```

**محفوظ ہونے کے اُس لمحے کی ٹری دیں** (ابھی کی ٹری نہیں)۔ کیونکہ محفوظ کاری میں
دیر لگنے کے دوران ٹائپ کیا گیا حرف بھی "بدلا ہوا" ہی رہنا چاہیے۔ محفوظ کرنے والی
wing (`save`) فائل واقعی لکھے جانے کے بعد اسے بلاتی ہے، اس لیے `.nabi` میں محفوظ
کرنے پر `isChanged()` کی قدر `false` ہو جاتی ہے۔

::: warning بنیادی خط صرف `.nabi` سے حرکت کرتا ہے
`.nhtml` یا `.md` میں جو نکلتا ہے وہ ایک **نقل** ہے، اور نقل بنیادی خط کو نہیں
سرکاتی — اس لیے محفوظ کرنے کے بعد بھی `isChanged()` `true` رہتا ہے۔ نقل کو "محفوظ ہوگیا" مان
لیں تو ونڈو بند ہوتے وقت بغیر پوچھے اصل لکھائی ساتھ لے جاتی ہے۔ محفوظ کرنا asynchronous ہو تو
بنیادی خط **صرف کامیابی کے بعد** سرکتا ہے — ناکام محفوظ کاری اسے ہاتھ نہیں لگاتی۔
:::

**واپس پہلی جگہ پر آ جانے پر بھی دوبارہ `false` ہو جاتا ہے** — کیونکہ nabi-tree
ناقابلِ تبدیل ہے اور ہر ترمیم پر پوری بدل جاتی ہے، تو دستاویز ایک جیسی ہے یا نہیں
یہ جاننے کے لیے چھاننے یا hash کرنے کی ضرورت نہیں، یہ اُسی جگہ معلوم ہو جاتا ہے۔

```ts
window.addEventListener('beforeunload', (e) => {
  if (nabi.isChanged()) e.preventDefault()
})
```
